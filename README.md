## ⚠️ 重启后桌面端会报一次「宿主停止」——功能是好的，报错是副作用

点重启后，桌面端会弹一个窗口，里面写着类似：

```
Error: dsh desktop host stopped: ...
```

**🫂 别慌。重启已经完成了，这只是外壳在汇报。**

原因贼直白 🧾：这插件的重启就是**真的把进程杀掉** 🔪
DSH Desktop 的外壳一直盯着自己的宿主子进程，发现它没了就尽职尽责地报一次 ——
它不知道这是你亲手按的电源键，它只知道自己被杀了 🥲

**关键是：新进程已经由 helper 在后台拉起来了** 🤖
你只需要**点「确定」或 ✕ 把窗口关掉**，然后刷新页面（插件也会自己找新实例并刷新）。

> 🔑 **一句话记住**：弹窗 = 外壳在汇报「宿主停了」；新宿主其实已经起来了。
> 关掉它、刷新，继续用 ✅

### 🤔 为什么这个弹窗消不掉（诚实交代）

我把 Desktop 主进程的代码翻了一遍，结论很明确：**它消不掉，插件层做不到。**

主进程 `main.js` 里监听着宿主子进程的退出：

```js
if (code !== 0 && code !== null) this.fail(...exited with ${code}...)
else this.fail(...stopped...)          // ← 退出码 0 也走 fail
```

**两个分支都调 `fail()`**，而 `fail()` 里只有一处闸门：

```js
if (!this.failureReported && !this.stopping) { this.onFailure?.(error) }
```

`stopping` 这个标志**只有主进程自己**在 `stop()` 里能设。插件跑在 host 子进程里，碰不到它 🙅

我还查了主进程的 IPC 白名单，只接受 `ready` / `shutdown-complete` / `platform-session` / `fatal` 四种消息，**没有任何一个能触发重启或优雅退出**。

所以：**只要是真的结束进程，主进程就必然汇报一次。** 这是外壳的固定行为，不是 bug，也不是本插件能绕开的。

### 🐛 试错记录（免得你也踩）

| 方案 | 结果 |
|---|---|
| 自己 spawn 新进程（`execPath + argv`） | ❌ 重开了 Electron 主进程，撞单实例锁和端口，弹 EADDRINUSE |
| `ELECTRON_RUN_AS_NODE` 只重放 host | ✅ 进程能起，但弹窗照旧（就是现在的方案） |
| 非零退出码，想让用户点弹窗里的「重启」 | ❌ 绕远了，而且点 ✕ 会把新进程一起关掉 |
| 退出码 0 | ❌ `fail()` 的 else 分支同样触发，只是文案从「exited」变成「stopped」 |

**最终方案**：helper 在后台接力拉起新进程（保证功能可用），接受外壳报一次「宿主停止」。
功能完整、一键完成、页面自动刷新——只是附带一个提示框。

> 💡 想完全避开这个框？用你桌面版菜单里的**「重启应用与 Host」**——那是官方 `app.relaunch()` 通道，
> 走正常退出流程，不弹窗。（本插件没走那条路，是因为插件够不到 Electron 主进程。）

## 🛠️ 它是怎么工作的（技术党进）

### ⚡ 重启

三段接力，没有任何魔法：

1. **自省** 🪞：从 `process.execPath` / `process.argv` / `process.execArgv` 现场问出「我是被谁、用什么命令启动的」
   - Desktop（我们是 Electron 的 host 子进程）→ `ELECTRON_RUN_AS_NODE=1` + `exe + execArgv + host 入口 + 原参数`
   - 普通 node 宿主 → 拼回 `node + execArgv + 入口 + 参数`
   - **不猜** profile 🙅 **不读**别人的配置 🙅 **不写死**路径 🙅
2. **接力** 🏃：拉起一个 `detached` 的 helper。它不在宿主进程树里，所以宿主退出时不会被连坐
3. **交接** 🤝：宿主退出 → helper 探测端口真的空出来 → 拉起新进程 → helper 自己退出

前端则是**持续 ping 直到通、然后刷新页面**——因为新进程的端口可能和原来不一样 🎯

### ⏻ 关闭

给 launcher 的 `appExit` 钩子打个招呼（没有钩子就直接 `process.exit(0)`），
外壳视为正常退出，**不弹窗** 😴

### 🔒 安全边界

- 只接受**同源** `POST`，跨站一律 403
- 端口只在本机 loopback 监听
- 除重启 / 关闭外没有任何其他动作

## ❓ 常见问题

**Q：重启后弹了「宿主停止」，是不是没重启成功？** 😰

成功了 ✅ 新进程已经由 helper 拉起来，弹窗只是外壳在汇报「旧宿主没了」。
**关掉弹窗、刷新页面**就行（插件也会自己找新实例并刷新）。

**Q：这个弹窗能彻底关掉吗？每次重启都弹好烦** 😤

不能，插件层做不到 🙅 详见上面「为什么这个弹窗消不掉」。
**但可以完全避开**：用桌面版菜单里的**「重启应用与 Host」**，那是官方 `app.relaunch()` 通道，走正常退出，不弹窗。

**Q：那我为什么还要用这个插件？** 🤔

因为它就在会话头部，两下点击，不用翻菜单；而且它**同时提供「关闭」**——现有同类插件几乎都只做重启。

**Q：重启后端口变了，我原来的浏览器地址打不开了？** 🤔

正常 🙂 DSH 会自己挑端口。重新从桌面应用或启动器进入即可。

**Q：为什么关闭不弹窗，重启却弹？** 🤨

关闭是你主动要它退出 😴 外壳视为正常退出；
重启是「先死一次再复活」🧟 外壳在中间那一刻看到的是「意外消失」，所以报了一次 📢
—— 而这个弹窗恰好就是我们借来重启的通道 🤝

**Q：能批量重启多个 DSH 吗？** 🤖

不能，它只管当前这一个进程。想开多个请用多 profile，别指望它变集群管理器 😅

**Q：关闭之后数据会丢吗？** 💾

不会 🙅 会话、配置、插件全都在磁盘上躺着。关闭只是让进程退出，不是删库跑路 🔥

## 🔬 自检

```bash
curl http://127.0.0.1:<port>/dsh-power-switch/api
```

返回里能看到当前 `pid` 🆔、`port` 🔌、`platform` 🖥️、`restartable` ✅

它不会撒谎 —— 如果 `restartable: false`，说明它没能推断出启动命令，这时候它会**拒绝**重启而不是瞎猜 🙅‍♂️（宁可不动，也不乱动，这点很讲究）
