## 👀 长什么样

会话头部右侧多一枚小电源图标 ⚡，**不抢位置**、**不遮**最小化 ➖ / 隐藏 👻 / 关闭 ❌ 那组窗口按钮（这点我盯得很死，谁也别想挤到它们）

点开是个小菜单，里面**只有两个按钮**，干干净净：

| 按钮 | 干了什么 |
| --- | --- |
| **⚡ 重启** | 结束当前进程 → 等端口让出来 → 按**原来的命令行**重新拉起一份 🔁 |
| **⏻ 关闭** | 结束当前进程，不自动拉起 🌙 |

两个按钮都要**点两次** 👆👆：
第一次是「你真的想好了吗 🤨」，第二次才是「好，动手 🔨」

## ⚠️ 重启时弹「应用无法启动或已意外停止」——这是正常的！别慌！

点重启后，屏幕上会跳出这么一个吓人的窗口 😱：

![重启时弹出的窗口，属正常现象](docs/restart-dialog.png)

**🫂 别慌，这是正常情况，不是坏了。**

原因贼直白 🧾：这插件的重启就是**真的把进程杀了** 🔪
DSH Desktop 的外壳发现自己怀里的宿主进程突然没了 💀，就尽职尽责地报了一次崩溃 ——
它不知道这是你亲手按的电源键，它只知道自己被杀了 🥲 所以它弹窗、写崩溃日志，然后安安静静等着。

紧接着，插件早就留好的那个 helper 进程 🤖 会把新的一份拉起来 🐣
等服务端口重新监听上，页面自己刷新，一切照旧 ✨

完整流程长这样 👇

1. 点「⚡ 重启」👆
2. 菜单里出现「正在重启，等新实例… ⏳」
3. 弹这个窗 → **正常** ✅ 它只是外壳在报告「我的宿主没了」，**不是重启失败**
4. 直接点 ✕ 关掉它（或者不理它），**不要**点「退出」/「重启」
5. ⏳ 几秒到十几秒，新实例就位
6. 🔄 页面自动刷新（端口变了也能找到），继续用

> 🔑 **一句话记住**：弹窗出现 = 进程真的死了 = 重启确实发生了。
> 它是个**事后通知**，不是失败提示。关掉它，刷新，就是新的 DSH。

窗口里那句 `MODULE_NOT_FOUND` 也是同一个道理 🧩：崩溃报告要写堆栈，而它被中断在启动早期，写出来就是这串。
**它真不是你插件坏了** 🙏 是「进程被突然打断」这件事本身的副产品。

### 🤔 为什么这个弹窗消不掉（诚实交代）

我把 Desktop 主进程的代码翻了一遍，结论很明确：**它消不掉，插件层做不到。**

- 弹窗由主进程的 `DesktopFatalRecovery.report()` 弹出，触发条件是「host 子进程非预期退出」。它靠内部一个 `shuttingDown` 标志区分「正常退出」和「意外死亡」，而这个标志只有应用自己的退出流程能设。
- 主进程确实有官方重启姿势：`app.relaunch() + quitWithoutConfirmation()`（就是开发版菜单里的「重启应用与 Host」）。但它在 **Electron 主进程**里，插件跑在 **host 子进程**里，够不着 🙅
- IPC 通道表里只有快捷键、目录选择、更新、主题这些，**没有任何一个能触发重启**。

所以：**只要是真的杀进程，主进程就必然报告一次。** 这是外壳的固定行为，不是 bug，也绕不过去。

### 🐛 那之前「点 ✕ 没重启」是怎么回事

那是我的锅 🫠 已经修了。原因很具体：

**第一版**用 `execPath + argv.slice(1)` 去拉新进程 —— 等于又开了一个 Electron 主进程 🚫 撞上单实例锁和端口占用，主进程判定「地址被占用」，于是弹框，而新实例根本没起来。所以你看到的现象就是「点完弹窗、点 ✕、什么都没变」。

**现在的做法**：用 `ELECTRON_RUN_AS_NODE=1` 把同一个 exe 当 node 用，只重放 **host 子进程自己**：

```
DeepSeek Harness.exe  (以 node 身份)
  + --expose-internals
  + .../dsh-desktop-host/lib/index.js
  + 原来的参数
```

这样主进程看到的是「我的 host 子进程换了张皮」，不涉及应用生命周期。实测新进程正常起来、插件自动挂载 ✅

另外 helper 以前是死等 15 秒再拉，现在改成**真正探测端口释放**（连得上就继续等，连不上才启动），避免撞端口。

> 💡 用「⏻ 关闭」则完全不会弹窗 —— 关闭是你主动要它走，DSH 会安静退出 😴
> 只有「重启」这种「先死一次再复活」的操作 🧟，外壳才会误以为出事了。

## 🛠️ 它是怎么「真的」重启的（技术党进）

没有魔法 ✨ 只有三段：

1. **自省** 🪞：从 `process.execPath` / `process.argv` / `process.execArgv` 现场问出「我是被谁、用什么命令启动的」
   - Desktop（Electron 运行时，但我们只是它的 host 子进程）→ `ELECTRON_RUN_AS_NODE=1` + `exe + execArgv + host 入口 + 参数`
   - 普通 node 宿主 → 拼回 `node + execArgv + 入口 + 参数`
   - **不猜** profile 🙅 **不读**别人的配置文件 🙅 **不写死**路径 🙅
2. **接力** 🏃：拉起一个 `detached` 的 helper 进程。它不在宿主进程树里 🌳 所以宿主退出时它不会被连坐 🛡️
3. **交接** 🤝：宿主退出 → helper **探测端口真的空出来** → 拉起新进程 → helper 自己也退出 👋

关闭更简单 😴：给 launcher 的 `appExit` 钩子打个招呼；没有钩子就直接 `process.exit(0)`

**关于端口** 🔌：新进程起来后端口可能跟原来不一样（DSH 会自己挑），所以重启完是**持续 ping 直到通、然后刷新页面**，而不是死守旧地址 🎯

## 🛡️ 安全边界

- ✅ 只接受**同源** `POST`，跨站请求一律 403 🚫
- ✅ 端口只在本机 loopback 监听，没往外暴露一丁点
- ✅ 不做「顺便帮你跑个命令」这种扩展 —— 它就两个动作：重启 🔁、关闭 🌙
- ✅ 关闭按钮**不会**删你的会话、配置或插件，只是让进程退出（数据都在，放心）

## ❓ 常见问题

**Q：点重启后弹了「应用无法启动或已意外停止」，是不是插件写坏了？** 😰

不是 🙅 这是主进程在报告「我的宿主子进程没了」，也就是**重启确实发生了** ✅
新实例由 helper 拉起，几秒后页面自动刷新。
**别点弹窗里的「退出」**（会打断接力），点 ✕ 关掉它就行 🏃

**Q：弹窗能彻底关掉吗？每次重启都弹好烦** 😤

不能，插件层做不到 🙅 详见上面「为什么这个弹窗消不掉」——它在 Electron 主进程里，而插件跑在 host 子进程里，够不着 `app.relaunch()`。
**但可以避开它**：用「⏻ 关闭」就不弹，因为你主动要它退出，外壳视为正常退出 😴

**Q：我点了 ✕，但好像没重启？** 🤔

这个坑我踩过 🫠 旧版本确实会这样（启动命令写错，撞了单实例锁）。现在已修：改成 `ELECTRON_RUN_AS_NODE` 只重放 host 子进程。
如果还遇到，打开菜单看有没有「正在重启，等新实例… ⏳」；有就说明正在跑，等它就好。

**Q：重启后端口变了，我原来的浏览器地址打不开了？** 🤔

正常 🙂 DSH 会自己挑端口。重新从桌面应用或启动器进入即可；页面里的自动刷新会跟着新端口走 🎯

**Q：为什么关闭不弹窗，重启却弹？** 🤨

关闭是你主动要它退出 😴 外壳视为正常退出；
重启是「先死一次再复活」🧟 外壳在中间那一刻看到的是「意外消失」，所以报了一次 📢

**Q：能批量重启多个 DSH 吗？** 🤖

不能，它只管当前这一个进程。想开多个请用多 profile，别指望它变集群管理器 😅

**Q：关闭之后数据会丢吗？** 💾

不会 🙅 会话、配置、插件全都在磁盘上躺着。关闭只是让进程退出，不是删库跑路 🔥

## 🔬 自检

```bash
curl http://127.0.0.1:<port>/dsh-power-switch/api
```

返回里能看到当前 `pid` 🆔、`port` 🔌、`platform` 🖥️、`restartable` ✅

它不会撒谎 —— 如果 `restartable: false`，说明它没能推断出启动命令，这时候它会**拒绝**重启而不是瞎猜 🙅‍♂️（宁可不动，也不乱动，这点很讲究）
