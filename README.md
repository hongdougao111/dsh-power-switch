# ⚡ dsh-power-switch · 一键电源开关

> 右上角多一枚电源键。
> 点一下，DSH Web 进程**真的死了**；再点一下，它**真的又活了**。
>
> 不是 `location.reload()`。不是 `router.refresh()`。不是「转两圈假装重启好了」。
> 是这个进程真的从任务管理器里消失，然后一个新的它站起来。

---

## 这玩意儿解决什么问题

装插件、改配置、调 patch 之后，DSH 经常要「重启一下才生效」。

然后你就开始了一套行为艺术：

1. 翻到任务管理器
2. 在一堆 `node.exe` 里猜哪个是 DSH
3. 猜错一次，把别的东西干掉了
4. 猜对一次，关掉
5. 忘了刚才的命令行是什么，凭记忆重敲
6. 端口被占，报错
7. 重开一个终端，`dsh web`，端口又变了，浏览器地址失效

`dsh-power-switch` 把这一整套压缩成**两次点击**（第二次是防误触，它有点礼貌）。

## 长什么样

会话头部右侧多一枚小电源图标，不抢位置、不遮最小化/隐藏/关闭那组窗口按钮。
点开是一个小菜单，里面只有两个按钮：

| 按钮 | 干了什么 |
| --- | --- |
| **⚡ 重启** | 结束当前进程 → 等端口让出来 → 按**原来的命令行**重新拉起一份 |
| **⏻ 关闭** | 结束当前进程，不自动拉起 |

两个按钮都要**点两次**：第一次是「你真的想好了吗」，第二次才是「好，动手」。

## ⚠️ 重启时弹「应用无法启动或已意外停止」——这是正常的

点重启后，屏幕上会跳出一个这样的窗口：

![重启时弹出的窗口，属正常现象](docs/restart-dialog.png)

**别慌，这是正常情况，不是坏了。**

原因很直白：这个插件的重启就是**真的把进程杀掉**。DSH Desktop 的外壳发现自己的宿主进程突然没了，会尽职地报一次崩溃——它不知道这是你亲手按的电源键，它只知道自己被杀了。所以它弹窗、写崩溃日志，然后安静等着。

紧接着，插件预先留下的那个 helper 进程会把新的一份拉起来。等服务端口重新监听上，页面自己刷新，一切照旧。

所以你看到的完整流程是：

1. 点「⚡ 重启」
2. 弹这个窗 → **正常**，说明进程真的死了
3. 别点「退出」也别点「重启」（点了就变成两次重启了），让它待着或者直接关掉这个窗
4. 几秒到十几秒后，DSH 自己回来
5. 页面自动刷新，继续用

窗口里那句 `MODULE_NOT_FOUND` 也是同一个道理：崩溃报告要写堆栈，而它被中断在启动早期，写出来就是这样一串。**它不是你的插件坏了**，是「进程被突然打断」这件事本身的副产品。

> 如果你**不想**看到这个弹窗，那就用「关闭」——关闭是你主动要它走，DSH 会安静退出。
> 只有「重启」这种「先死一次再复活」的操作，外壳才会误以为出事了。

重启之后页面会自动等你，服务一回来就刷新。

## 它是怎么「真的」重启的

没有魔法，只有三段：

1. **自省**：从 `process.execPath` / `process.argv` / `process.execArgv` 现场问出「我是被谁、用什么命令启动的」。
   Electron 宿主就直接重放 `execPath + argv.slice(1)`；普通 node 宿主就拼回 `node + execArgv + 入口 + 参数`。
   不猜 profile、不读别人的配置文件、不写死路径。
2. **接力**：拉起一个 `detached` 的 helper 进程。它不在宿主进程树里，所以宿主退出时它不会被连坐。
3. **交接**：宿主退出 → helper 等端口释放 → 拉起新进程 → helper 自己也退出。

关闭更简单：给 launcher 的 `appExit` 钩子打个招呼；没有钩子就直接 `process.exit(0)`。

**关于端口**：新进程起来后端口可能和原来不一样（DSH 会自己挑），所以重启完是**等 ping 通就刷新页面**，而不是死守旧地址。

**关于那个崩溃弹窗**：DSH Desktop 的外壳把「宿主进程消失」当成异常，会弹窗、写崩溃日志。这是我们主动杀进程的必然副作用，不是故障——helper 会把新进程拉起来，页面随后自动恢复。详见上面的[说明](#️-重启时弹应用无法启动或已意外停止这是正常的)。

## 安装

插件市场里搜 **电源** / **power**，或者：

```bash
dsh plugin add dsh-power-switch
```

装完重启一次 DSH（对，就用它自己）。

## 安全边界

- 只接受**同源** `POST`。跨站请求一律 403。
- 端口只在本机 loopback 上监听，没有对外暴露任何东西。
- 不做「顺便帮你跑个命令」这种扩展——它就两个动作：重启、关闭。
- 关闭按钮不会删你的会话、配置或插件，只是让进程退出。

---

## 兼容

- DSH Web 与 Desktop 双端。
- Desktop 下进程本体是 `DeepSeek Harness.exe`，重启走 `electron-exec` 路径，重放整个应用启动参数。
- 普通 `dsh web` / `node bin.js` 启动的宿主走 `node-entry` 路径。
- 两条路径都由 `GET /dsh-power-switch/api` 的 `facts` / `restartable` 字段如实自报。

## 常见问题

**Q：点重启后弹了「应用无法启动或已意外停止」，是不是插件写坏了？**

不是。这是重启生效的**证据**：进程真的死了，外壳才会报错。等几秒，helper 会把它拉回来，页面自动刷新。不要点弹窗里的「退出」，否则会打断接力。

**Q：重启后端口变了，我原来的浏览器地址打不开了？**

正常。DSH 会自己挑端口。重新从桌面应用或启动器进入即可；页面里的自动刷新会跟着新端口走。

**Q：为什么关闭不弹窗，重启却弹？**

关闭是你主动要它退出，外壳视为正常退出；重启是「先死一次再复活」，外壳在中间那一刻看到的是「意外消失」，所以报了一次。

## 自检

```bash
curl http://127.0.0.1:<port>/dsh-power-switch/api
```

返回里能看到当前 `pid`、`port`、`platform`、`restartable`。
它不会撒谎——如果 `restartable: false`，说明它没能推断出启动命令，这时候它会**拒绝**重启而不是瞎猜。
